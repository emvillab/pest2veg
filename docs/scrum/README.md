# Scrum evidence and completion plan

Prepared 25 October 2026. This pack separates recorded development activity from proposed planning. It does not reconstruct attendance, invent meetings or certify full Scrum adherence.

## Recorded evidence

The existing README names five team members and responsibilities. Git history records iterative changes, research uploads, feature/fix branches and pull-request merge subjects; see git-evidence.md and commits.csv. The parent-folder PDF `Pest_Detection_Team_Project_Plan.pdf` is an earlier proposed plan with a four-week schedule, milestones and risks. It explicitly says names/roles require approval and is not confirmation of completed work. A reference copy is retained under reference/.

There are no verified historical stand-up attendance lists, sprint planning decisions, reviews, retrospectives, accepted backlog records or remote review approvals in this supplied evidence set. A local history snapshot is useful collaboration evidence, but cannot fill those gaps.

## New planning records

- backlog.csv: implemented baseline and remaining acceptance work; statuses distinguish code present from verified Done.
- completion-plan.md: proposed schedule and Gantt/milestones from 25 October onward; owners/dates require team agreement.
- risk-register.csv: current risks and proposed responsibility.
- standup-log-template.csv: blank future meeting record. Fill it only after an actual meeting.
- sprint-review-template.md: blank future review and retrospective prompts.

Recorded roles are reproduced from the existing README. Product Owner is not recorded; agree who prioritises and accepts the backlog. Do not assume the tutor holds this role. Proposed tasks use role names until individuals accept them.

## Definition of Done for the completion work

The responsible member provides the artefact or code, links relevant tests/manual evidence, records known limitations, reconciles affected documentation, obtains an actual peer review and records team acceptance. An implemented feature with browser checks outstanding remains 'Implemented; validation pending'. A commit alone does not establish Done.

## Recovering missing genuine records

Members can supply dated task-board exports, actual meeting notes, tutor feedback, messages confirming decisions and PR review records. Retain their original timestamps and sources. A retrospective recollection should carry today's date, the author's name and an explicit recollection label, with corroborating links where available. If no record exists, leave the gap visible. Record actual future stand-ups, reviews and changes from now on.
